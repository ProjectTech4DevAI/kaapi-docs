# Content Safety

**Runs on incoming messages**

Removes abusive or hurtful words from messages before the assistant reads them.

## What happens

**↻ Fixes & passes on** — The message continues as normal, with the abusive word hidden. The user is not interrupted.

## Example

| | |
| --- | --- |
| **User** | `Don't be such an <slur>, you know?` |
| **Assistant sees** | `Don't be such an [REDACTED_SLUR], you know?` |

The word is hidden before the assistant reads the message.

:::info

Works only when the incoming message is in English, Hindi or Hinglish. Messages in other languages pass through unchecked.

:::

## Without this guardrail

:::danger

The abusive word reaches the assistant, and may appear again in the reply. **Risk:** abusive language is not stopped, which hurts trust and looks bad for your organisation.

:::

## Settings

Validator: `content_safety`. It first replaces slurs from an English and Hindi list with `[REDACTED_SLUR]`, then scores what is left for profanity.

| Setting | Values | What it does |
| --- | --- | --- |
| `slur_severity` | `low`, `medium`, `high`, `all` (default `all`) | Minimum slur severity to hide. |
| `profanity_threshold` | `0`–`1` (default `0.9`) | Profanity score at which the message fails. 0.9 avoids blanking common Hinglish like `kaise ho`. |

## How well it works

<MetricsHeadline validator="content_safety" />

Tested on real-style messages in English, Hindi and Hinglish.


## Known limitations

:::warning

- **It misses a sizeable share of toxic messages on real-world data.**
- **Hindi in Devanagari script is caught less often**, because Hindi slurs are caught only by the slur list.
- **If profanity remains after slurs are hidden, the message is blanked** — there is no partial fix.
- **Hiding a slur lowercases the whole message and removes emoji.**

:::
